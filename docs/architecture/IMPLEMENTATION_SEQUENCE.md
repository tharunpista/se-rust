# Implementation sequence

Phases follow charter §14. The ordering below encodes **real prerequisites**, not preference: each phase's work is blocked by something concrete in the phase above it.

Every phase ends with the full gate: `cargo test --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo fmt --all -- --check`, `cargo build --release`, plus a manual run of the release binary in Windows Terminal. Unit tests cannot prove terminal protocol behaviour, so terminal claims require the manual run.

## Prerequisite chain (the part that is not negotiable)

**Corrected after two independent Phase 0 reviews** (`solution-architect`, `security-architect`). The first version misplaced E9 and described E7 inaccurately; both are fixed below, and a fourth chain (E10) was missing entirely.

```
E7 reconciliation (two ids → one; TaskId on the decision; bind to canonicalized target)  ──►  tool permission gateway  ──►  native tools
E9 fix (recv_timeout + cancellation recheck) + the two open §11 items  ──►  Phase 2a, NOT the team scheduler
E8 fix (task-id-routed approvals, per-task history) + worker pool + semaphores  ──►  team scheduler  ──►  task DAG execution
E10 (cleared child environment)  ──►  the shell tool specifically, not "the tool system" generally
session persistence  ──►  resume
agent loader  ──►  agent invocation  ──►  team orchestration
```

Consequences, corrected:

- **The tool gateway cannot be built before E7 is reconciled.** The original description of E7 was wrong: call-id correlation already exists and is tested (`sink.rs`, `engine.rs`'s stray-decision regression test). What is actually open is narrower and still blocking — `request_approval` and `tool_requested` mint two different ids for the same call; the decision carries no `TaskId`; and nothing binds the approved bytes to a canonicalized, execution-time-verified target (a hash of the display string does not survive a symlink, relative path, glob, or Windows path-aliasing substitution — see `SE_TARGET_ARCHITECTURE.md` §3a). All three must close before the gateway, or the gateway ships the gap into the one component whose job is authorization.
- **E9 is reachable today, single-task, and must be fixed in Phase 2, not deferred to the scheduler.** The approval channel is 1-slot with every send as `try_send` (error discarded), and the approval-wait loop blocks on a bare `recv()` with no cancellation recheck. The moment any real tool exists (Phase 2 step 4), a stray decision or a concurrent interrupt can park the worker forever — this has nothing to do with multiple tasks. Fix is a `recv_timeout` loop rechecking cancellation each pass; two lines, not a scheduler rework.
- **The team scheduler cannot be built before E8 is fixed.** E8 — `Approve`/`Interrupt` ignoring task id, a shared `History` mutex — is the genuine multi-task defect and stays scheduled for Phase 4, where the worker pool and semaphores are built anyway.
- **E10 has no phase slot in the original sequence, despite Phase 2 shipping a shell tool that needs it immediately.** The first `Command::new` in the codebase inherits every provider API key and base-url override into a model-authored command. Added below as Phase 2 step 4a, immediately before the shell tool.
- **Resume cannot be claimed before persistence exists.** Today history is in-memory (`crates/se-core/src/engine.rs`); there is nothing to resume from. Additionally: **the userinfo/transport-redaction fix (§11, E6) must land before persistence**, or one release of durable session history writes unredacted credential-bearing URLs to disk before the fix exists. Reordered below.
- **Audit-record durability has no owner.** `se-permission` is specified as a decision function plus an audit sink with no durable store named, so approvals could not be reconstructed after a restart, and a persisted `Approved` token must not be honoured after resume. Named explicitly in Phase 2a below.

## Phase 2a — Runtime correctness and durability

**Split from the original single Phase 2**, per the `solution-architect` review: the original phase bundled five independently-failable subsystems behind one gate sentence that only exercised the last of them. This half has nothing in it that depends on the gateway.

1. **Redaction fix first, before persistence exists**: reject URL userinfo at the one shared point where `is_safe_origin()` and `origin_of()` parse an authority; wrap both `Transport(t.to_string())` sites in `first_line()`; never echo a URL in an error message.
2. **E9 fix**: `recv_timeout` loop in the approval wait, rechecking cancellation each pass. Regression test: a stale decision queued, then an interrupt, must free the worker (not reproduced yet — write it before calling this fixed).
3. **Cancel-vs-deadline precedence, made testable**: extract the tie-break into a pure function with a four-row truth table (deadline × cancel, both orderings); cover the second override site in `engine.rs` in the same table.
4. **Keyless-provider HTTPS gap (E6b)**: require loopback or https for a keyless service too — not arbitrary remote `http://` — since a keyless provider is a *data*-confidentiality boundary, not just a credential one.
5. **DONE, scoped down from the original item.** `se-core::session_store` is an append-only log of the same `CoreEvent`s the core already emits -- one schema, no migration machinery, because adding a second format nothing writes yet would be speculative. `CoreHandle::attach_session_log` wires it into `drain`/`drain_blocking`, the single choke point every event already passes through, so persistence needed no change to the supervisor loop or the three-thread model. `reconcile()` reads a log back and reports each task's real state — `Finished { outcome }` exactly as the core reported it, or `Interrupted` for a task with a start but no terminal event, never silently upgraded to completed and never replayed. Wired into the real `se` binary's interactive path under `.se/sessions/<session-id>.jsonl`; a logging failure folds into the existing banner rather than refusing to start. **Explicitly not built, and not pretended to be:** undo/redo. A model turn is not a reversible edit and its semantics are not yet defined, so inventing an "undo" now would be exactly the speculative abstraction already rejected elsewhere in this project — resume-only is the honest scope. Checkpoints are the event log itself; there is no separate checkpoint format. The rule that a persisted `Approved` token is never honoured after resume is recorded in `SE_TARGET_ARCHITECTURE.md` §3a as a requirement on the token design and remains to be enforced once that token exists (Phase 2b) — nothing to resume yet since no tool system exists.
6. **DONE.** The model-resolution prerequisite §6.6 needs: `UserTurn` gained `model: Option<ModelRef>` in `se-protocol` (level 1, the task override), `se-core::routing::resolve(task_override, specialist, team, department, global)` encodes the full five-level precedence with an actionable sixth-level error, and `CoreHandle::submit_with_model` is the seam a `/model` command or a specialist profile will call once either exists. `ProviderRunner` does not yet consult any of this — it still runs with the provider/model it was constructed with, fixed for the process's lifetime — so a submitted override is accepted by the protocol and the resolver but has no effect on what actually executes until `ProviderRunner` (or its replacement) is made registry-backed. That wiring is real remaining work, not yet started.

**Gate:** kill the process mid-turn; on restart the task reads `interrupted`, never `completed`. A stray approval followed by an interrupt frees the worker (regression test, not a self-report). The cancel-vs-deadline truth table passes all four rows. A credential-bearing URL with userinfo is refused, and the refusal message never contains the URL. A keyless provider refuses a non-loopback `http://` base URL. `UserTurn` can carry an explicit model override and `resolve()` picks it over every lower level.

## Phase 2b — Authorization and tools

1. **E7 reconciliation, part one DONE**: one `ToolCallId` per call. `tool_requested` and `tool_completed` no longer mint their own id; `request_approval` returns `Option<ToolCallId>` and callers pass that same id through. Proven end-to-end by `the_approved_call_id_is_the_same_id_the_tool_actually_runs_and_completes_under`, which drives a real `ApprovalRunner` through a real `CoreHandle`. Remaining, correctly deferred to this phase rather than fixed early: `TaskId` added to `ApprovalDecision`; the `Approved` token per the corrected design in `SE_TARGET_ARCHITECTURE.md` §3a (canonicalized target + OS-level identity, session+task id, tool name+schema version, cwd/env subset, single-use nonce, the exact bytes shown to the human) — not the bare argument-hash first proposed. `#[cfg(test)]`-gating `ApprovalRunner`/`TwoApprovalRunner` was tried and reverted (it breaks `se-tui`'s cross-crate tests, which rely on the same un-gated convention `EchoRunner` already uses); the id fix itself is what mattered.
2. **E10: DONE.** `crates/se-core/src/tools/shell_env.rs` clears the child environment (`Command::env_clear()`) and rebuilds it only from a named `ENV_ALLOWLIST` (`PATH`, `TEMP`, `TMP`, `SystemRoot`, `windir`) plus whatever the gateway's `Approved` token itself bound as `env_subset` -- never the parent process's inherited environment. `a_parent_only_secret_does_not_reach_the_spawned_child` sets a secret in the test process, spawns a child that dumps its own environment, and asserts the secret is absent -- the test that would fail if this were ever "simplified" back to inheriting. `an_explicitly_bound_env_var_does_reach_the_child` proves the allowlist discriminates rather than blocking everything. Scope preserved exactly as flagged: this is env scrubbing, not isolation -- a same-user child can still read Credential Manager directly; a low-privilege user or AppContainer is a separate, later decision, not built here.
3. **`se-permission` gateway: DONE for the decision function and the token; the audit sink's durability is still open.** The crate is a workspace member with `se-protocol` as its only dependency and no `fs`/`std::process` use at all, which is what keeps it unit-testable without starting anything. `Ruleset::evaluate` is last-matching-rule-wins over `(agent, tool, resource_scope)` patterns and returns `Effect::Ask` when no rule matches -- an unconfigured gateway is never a silent grant, proven by `empty_ruleset_defaults_to_ask`. `Approved`'s fields are private and its only constructors are `Gateway::decide` (on an `Allow` effect) and `Gateway::approve` (the human-approved `Ask` path); `decide` deliberately mints nothing on `Ask`, so a ruleset edit cannot grant what a human has not yet answered. The token carries every field named in `SE_TARGET_ARCHITECTURE.md` §3a and `verify_and_consume` re-checks them against an `ExecutionContext` the caller builds from what it is *about* to do, rather than trusting the token's existence: `a_token_rejects_a_changed_resource_at_execution_time` is the symlink-swap case, `a_token_rejects_an_agent_whose_definition_changed_since_approval` the edited-agent-body case, `a_token_cannot_be_spent_twice` the replay case, and `an_expired_token_is_rejected_even_with_a_matching_context` the stale-token case. Expiry and single-use are checked *before* the field comparison so a replayed token never learns which field would have mismatched. The nonce ledger is in-memory only and never persisted, which satisfies "a persisted token must never be honoured after resume" structurally rather than by a separate invalidation step. `AuditRecord` keeps env-var *names* and drops their values, so a secret is never in the record to need redacting. **Deliberately not built here, and not pretended to be:** path canonicalization and OS-level file identity are *not* in this crate -- `ResourceIdentity` is an opaque string the caller resolves, because the architecture doc puts this crate's boundary at "a pure decision function" and a crate that resolved paths could itself be tricked by one changing meaning. Resolving it correctly on Windows (drive-relative, 8.3, `\\?\`, UNC, case-insensitivity) belongs to the `se-core` tool path in step 4. `NullAuditSink` is the only sink shipped; a durable one is still the open question recorded above, not a thing this crate silently invented. No `se-core` wiring yet -- nothing in `se-core` executes a tool, so there is no path that could require a token, and adding the dependency before step 4 would be an unused edge in the crate graph.
4. **Native tools (read/write/edit/search/shell): DONE, standing alone, not yet wired into the model loop.** Live under `crates/se-core/src/tools/` (`se-core` now depends on `se-permission`). `Granted` is the type-level proof the architecture doc asked for: its only constructor runs `Approved::verify_and_consume` against a `NonceLedger` and returns the proof only on success, with private fields and no other path to construct one -- a tool function takes `&Granted` as its first argument, so calling one with no successful verify in hand is a compile error, not a runtime check. `se-permission`'s own API was not touched; `Granted` wraps it. `identity.rs` is the Windows/Unix `ResourceIdentity` resolver `se-permission` deliberately left to its caller (that crate never resolves paths itself, so it cannot be fooled by one changing meaning) -- Windows resolves by volume serial + file index via `GetFileInformationByHandle` (one new pinned dependency, `windows-sys`, FFI signatures only), Unix by `dev`+`ino`. `a_symlink_and_its_target_resolve_to_the_same_identity` proves both halves of the §3a claim against the real resolver, not a hand-built fake string: a symlink (or hard-link fallback under restricted privilege) to the same file resolves identically, and a delete-and-recreate at the same path -- the actual TOCTOU swap -- resolves differently. Every tool calls `require_fresh_identity` before touching a path that already exists; a not-yet-existing path (new-file `write`) has nothing to compare against and is documented as accepted without that check, not silently skipped. Five tools: `read_file`, `write_file`, `edit_file` (refuses an absent-or-ambiguous match and leaves the file untouched -- proven, not assumed, by a test that checks the file is byte-identical after a refused edit), `search_text` (hand-rolled recursive substring scan, no new regex dependency), `run_shell` (the E10 fix point, above). **Still open, correctly left to the next step**: `ExecutionContext` carries no `resource_scope` string (only the resolved `ResourceIdentity`), so each tool re-resolves and compares the real `&Path`/cwd the caller passes in, rather than trusting a stored scope -- which is the right re-check but puts the burden on whoever builds the `ExecutionContext` to pass the same path both times; not wired into `ProviderRunner` or any model-facing loop (step 5); no low-privilege containment (E10's own stated boundary, not a gap introduced here).
5. **DONE.** `ProviderRunner::run` now loops across model round trips rather than making one request per turn. A round that ends in `finish_reason == "tool_calls"` pushes the assistant's own `Message::assistant_tool_calls`, runs every call through a real `se_permission::Gateway::decide`/`approve`, and pushes exactly one `Message::tool_result` per call -- a denied or errored one included, so the model is told why a call did not run rather than the turn silently stopping. The approval mapping (left to the caller by `se-permission`): `Decision::Deny` is checked before any human is asked and is final; `Decision::Allow` also never asks a human, the pre-minted token is used directly; `Decision::Ask` is the only path reaching `TurnSink::request_approval`, where a "no", a cancellation and a disconnected interface are all treated identically as refusal. Cancellation is rechecked between every call and every round, not just once; one `turn_started`/`turn_deadline` pair, computed once, bounds the whole loop rather than resetting per round trip; usage sums across rounds instead of reporting only the last one's. `se-provider` gained the OpenAI-compatible wire format for this: request-side `tools`, and response-side per-index argument accumulation across SSE frames (a call's JSON arguments arrive incrementally; `StreamEvent::ToolCallRequested` fires only once a frame's `finish_reason` says the call is whole). `crates/se-core/src/tool_loop.rs` parses a call's JSON arguments into exactly what the gateway and the five tools need -- five small per-tool extractions, not a generic schema validator, since every field already fails closed on missing-or-wrong-typed. The still-open item 4 question (no `resource_scope` on `ExecutionContext`) is resolved here by construction: a not-yet-existing write target binds its token to the parent directory's identity rather than skipping the check, and every other call resolves the real path at the moment of the request.
6. **DONE.** `decision_is_invariant_under_every_field_a_model_change_could_plausibly_touch` in `crates/se-permission/src/lib.rs`. `Request` (and `ExecutionContext`, and `Rule`) carry no field that names a model or a provider at all, which is itself the proof charter §11 asks for: a decision cannot depend on something it has no way to receive. Not a vacuous test by inspection alone: it drives `Gateway::decide` through many requests identical in agent/tool/resource but varying every field a future per-model rendering difference could plausibly attach to a request (`agent_definition_hash`, `cwd`, `env_subset`, `shown_to_human`), and asserts every one decides identically because none of those fields reach `Ruleset::evaluate`. The test's own doc comment names the condition under which it would stop proving this: the day a model-identifying field is added to `Request`, this test is what must be extended, not silently kept green.

**Gate:** a configured native provider executes a real coding task with tool approvals, session history and verifiable output. Every tool invocation has exactly one matching gateway decision in the audit record, asserted by count, not inspection. A denied call does not execute. No tool path is reachable without an `Approved` token. Mark live-provider status separately and only with explicit authorization for a paid call.

## Phase 3 — SE specialist integration

1. **DONE for the agent half.** `crates/se-catalogue` is a new workspace member -- a pure read-only scanner, no dependency on `se-core` or anything execution-shaped, matching the `se-permission` pattern (`se-core` will depend on it, not the other way around; nothing wires it into `se-core` yet, since nothing downstream needs it until step 3). `load(root)` scans `<root>/<department>/<id>.md`, splits each file's `---`-delimited frontmatter from its body, and parses the frontmatter with `serde_yaml_ng` -- a maintained YAML crate, not a hand-rolled parser, because the real frontmatter has folded block scalars (`>-`), a nested `memory_scopes: {read, write}` map, and a list of `{mode, guard}` objects under `failure_modes`; getting folded-scalar continuation right by hand across 194 real files is exactly the class of bug a tested YAML implementation already covers, unlike `se-command`'s markdown frontmatter (flat key:value only, correctly hand-rolled there). Tested against the **real** on-disk catalogue, not only synthetic fixtures (`crates/se-catalogue/tests/real_catalogue.rs`, skipped gracefully if that machine-specific path is absent): all 194 real definitions load, `ownership-matrix.md` and `role-inventory.md` are reported as skipped with a reason ("no frontmatter block") rather than silently dropped or mis-parsed as agents, every id is unique, and loading the tree twice in a row produces identical content hashes -- the gate's own "hash the tree before and after" check, run against the real tree. Each loaded `AgentDefinition` carries a `content_hash` (`std::hash::DefaultHasher` over the raw file bytes -- a deliberate scope choice: this is an accidental-change/pinning check within a single trusted machine, not a cryptographic integrity guarantee against a malicious editor, which was never the threat this loader is positioned to cover; `se-permission`'s own `agent_definition_hash` field is a separate, security-relevant use this loader does not yet feed). A stray `.md` directly under the catalogue root is scanned as a candidate (reported skipped-with-reason if it fails to parse), but a non-`.md` file or a file nested more than one department level deep is ignored outright, not reported -- the distinction the loader draws between "not a candidate" and "a candidate that failed." **Not built here**: the skill half of this item (skills live in a different directory shape and were deliberately left to item 2, below, rather than guessed at); no wiring into `se-core`, `se-tui`'s `/` picker, or any invocation path (items 2-4); no directory watcher, per the architecture doc's own instruction.
2. **DONE.** `se_catalogue::load_skills(roots)` scans `<root>/<skill-name>/SKILL.md` across the three real skill roots on this machine (`SE\se\skills`, `SE\.agents\skills`, `~\.claude\skills`) and merges them, tagging each result with the root it came from; a name colliding across roots is reported as two entries rather than resolved, since precedence is a decision for whatever calls this loader, not this crate's job. Bodies are genuinely lazy, proven rather than merely designed that way: the scan reads raw bytes and decodes only the YAML frontmatter slice to UTF-8, never the body, which `a_body_with_invalid_utf8_still_scans_but_fails_only_when_the_body_is_actually_read` proves empirically -- a file whose body is not valid UTF-8 still scans successfully; only `load_skill_body`, called on demand per skill, fails on it. Read-only foreign-source scanning confirmed against the real `~\.claude\skills\synced` directory, which holds unrelated sync-manifest junk with no `SKILL.md` inside it -- correctly treated as "not a candidate" rather than reported skipped, the same not-a-candidate/failed-candidate distinction the agent loader already draws.
3. **DONE for browse/inspect/invoke; search is the existing picker filter, not a new mechanism; per-specialist tool narrowing is the one real gap left.** `se agents` / `se agents <id>` (CLI) are unchanged from before. New: typing `/<agent-id> <request>` in the TUI dispatches a turn routed through that specialist. The design keeps the catalogue off the interface thread entirely, per I1: `UserTurn` gained only a bare `specialist_id: Option<String>` (free to set); `CoreHandle::submit_specialist` does no catalogue I/O at all and reuses the existing `SubmitError` unchanged. The actual `se_catalogue::load` + lookup happens once inside `ProviderRunner::run`, on the worker thread -- the same place this crate already does blocking HTTP -- before the tool-call loop starts, and the resolved body is reused for every round trip in that loop; a test spans two round trips (forced by a ruleset denial) and asserts byte-identical system-prompt text on both. An unknown specialist id or a runner with no `catalogue_root` configured fails the turn with a clear `Outcome::Failed` message, same shape as an unregistered provider already uses, and never calls the model provider at all (asserted by request count, not inspection). `se-command` gained `HandlerKind::SpecialistInvoke`; each specialist's `CommandSpec.id` is namespaced `specialist:<id>` specifically so it can never collide with a short builtin id under the registry's same-id-is-a-reload rule, while `.path` stays the bare catalogue id a user actually types. The picker's existing live-query substring filter works on anything in the registry, so specialists get "search" for free -- confirmed, not reinvented. `se-tui` gained zero new runtime dependency (`se-catalogue` does not appear in its `Cargo.toml`); the binary builds the specialist `CommandSpec`s from its own existing `catalogue_root()`/`se_catalogue::load` call (the same one `se agents` already makes) and passes them into `se_tui::run`'s now-widened signature, folding a load failure into the startup banner rather than refusing to start, same convention session logging already uses. Selecting a specialist with no trailing text (exactly what the picker's accept path does today) is refused with a notice rather than submitted as an empty turn. **`tools:` narrowing DONE in `9e9d416`**: `Gateway::decide_scoped` intersects a specialist's `tools:` allowlist with the operator ruleset (never a union), resolved once per turn in `ProviderRunner::run`. **Still open**: `context_budget_tokens` and `max_calls` have no consumer.
4. **DONE.** `Payload::SpecialistInvoked { agent_id, content_hash }`, emitted once per specialist-routed turn right after `TurnStarted` (from the same catalogue read item 3 already does, never a second one), flows through the existing `session_store` -- which logs every `CoreEvent` verbatim with no allow-list -- so the record is durable and inspectable with no second storage path built. "Pinned for the run, never re-read mid-run" is the same structural fact item 3's test already proves: one `se_catalogue::load` call per turn, before the tool-call loop starts, its result reused (never re-fetched) across every round trip inside that one turn.

**Gate:** met for single-turn dispatch. A real specialist is invoked by its real id (`/backend-lead <request>` in the TUI, proven end to end by a test driving a real `CoreHandle`); its definition (content hash) and the turn's output are both recorded and inspectable via the session log; the catalogue is read-only throughout (`se-catalogue`'s own tests already hash the tree before and after). Not yet covered by this gate: multiple specialists collaborating in one run (that is Phase 4's task graph, not this phase's). Per-specialist tool narrowing closed in `9e9d416`.

## Phase 4 — Multi-model team orchestration

1. Bounded worker pool + per-provider/account semaphores; **E8 fixed here** (task-id-routed approvals, per-task history; E9 was believed fixed in Phase 2a, but see below).
   **Partly done: pool and task-id routing are done; per-task history and semaphores are open.** `se_core::start_pool(runner, n)` runs up to `n` tasks, each on its own worker; `start` is `start_pool(_, 1)`, so the interactive TUI still runs one task at a time until item 7 (file-conflict safety) exists. `ApprovalDecision` gained `task: TaskId`; the supervisor routes both `Approve` and `Interrupt` by task id, and a decision or interrupt for a task that is gone is dropped. Row 4.8: `approving_one_task_never_runs_another_tasks_waiting_call` (B emits nothing, runs nothing, after A is approved) and `interrupting_one_task_leaves_the_other_running`. Row 4.1: `two_tasks_in_a_pool_overlap`, proven from event order, not wall-clock. Per-task history: **closed for team work** by `start_isolated_pool` (item 3); the interactive chat keeps one shared transcript on purpose. Background: a task's in-flight messages are local (`provider_runner.rs` builds its own `messages` from the snapshot). But the shared `History` still exists, so with a pool above 1 a later task's snapshot can include another task's finished exchange. That is acceptable for one chat transcript and wrong for isolated team tasks (row 4.4). Item 3's task graph must give each task its own context.
   **One E9 drop path, missed in 2a, is now closed.** The pre-existing `a_stray_decision_never_approves_a_later_tool_call` "flake" was a real lost decision: a stray duplicate occupying the 1-slot approval channel made the supervisor's `try_send` silently drop the user's real answer, hanging the task. Per-task approval channels are now unbounded with a plain `send`. Evidence: a 30× se-core run at 16 test threads fails 2/30 with the old channel and 0/30 with the new one. That is strong evidence, not proof. Row 4.9 is now pinned deterministically by `a_reply_delivered_before_the_worker_parks_is_still_observed`. `TurnSink::request_approval` was split into `announce_approval` + `await_decision`, so a gated runner can have three strays and the real answer delivered before it parks. The test fails every time against the old 1-slot channel.
   **Still open:** per-provider/account semaphores. They are meaningless until `ProviderRunner` picks a provider per turn (2a item 6 wiring); today one core has exactly one provider, so the global cap is the per-provider cap. Marked as a `shortcut:` comment on `start_pool`.
2. Per-agent credential scoping (a free-function loader keyed only by service id means any task can trigger a read of any provider's key — closed before concurrent tasks exist).
   **DONE.** `ProviderRunner::authorize_provider` is the single gate before any model call. The operator's default provider and direct user turns pass. A specialist turn using any other provider's credential goes through the gateway as `use_provider` on `provider:<id>`: a ruleset `Deny` fails the turn without asking, `Ask` prompts the human once, and every outcome is audited. Tool calls in a specialist turn are now decided and audited under the specialist's own id and definition hash, not the shared `native-tool-loop` identity, so rules can target a specialist. Tests: `a_specialist_using_a_non_default_provider_needs_approval`, `a_ruleset_deny_blocks_a_specialists_provider_without_asking`, `a_specialists_tool_calls_are_audited_under_its_own_id`. ## Product direction (decided 2026-11-16)

SE stays a standalone CLI agent. Its differentiator: **several vendors' models working on one task at once, sharing context, with the 194-specialist catalogue chosen automatically**, fully configured from files. Built this round:
- **Per-node model + per-vendor limits**: `NodeSpec.model`, `team::Limits { max_concurrent, per_provider }`; a vendor at its cap waits while others proceed.
- **Native Anthropic (Claude)**: `Wire::Anthropic` on the shared client (`/messages`, `x-api-key`, `anthropic-version`), so origin pinning, no-redirect, redaction and timeouts are shared. Body and stream parser in `se-provider/src/anthropic.rs`, unit-tested and tested end to end against a mock server. Not live-verified against the real API.
- **Context passing between agents** (Phase 4 item 4, core): each node receives its dependencies' outputs fenced as DATA; `<<<` inside model output is broken up so injected text cannot close the fence. Capped at 64k chars (`shortcut:`). Outputs are journaled, so a resumed run still hands them on.
- **Automatic specialist selection** (`se-core/src/router.rs`): a turn naming no specialist gets one by two short multiple-choice questions to the turn's own model (department, then role), each answer validated against the catalogue, then keyword fallback, then a plain turn. On by default in the binary.
- **`se team run <file.yaml>` / `se team resume <journal>`**: team files (`team::file`) with per-task agent (optional = automatic), model (`provider/model`), deps and per-vendor limits. Naming a vendor in the file is consent to use its credential (`use_provider` rules derived from the graph, so resume gets the same consent). Smoke-tested with the real binary against a local mock LLM: two vendors, concurrent branches, auto-routing to real catalogue bodies, fan-in context.
- **Fixed**: `se exec` never answered approval requests, so any tool needing approval hung forever. It now asks on the terminal and denies when there is none.
